# Netlab 개발 운영 컨테이너화를 위한 문제 분석과 리팩토링 요청서

작성 기준일은 2026년 10월 23일이다. 이 문서는 향후 구현을 위한 요청서이며,
아래 목표 구조나 API가 현재 구현돼 있다는 의미는 아니다.

개발과 운영의 Netlab 앱을 같은 호스트의 독립된 컨테이너로 실행하고, 실습 환경은
호스트 LXD의 VM으로 유지한다. 개발에서 검증한 동일한 이미지로 운영을 배포할 수 있게 하되,
개발 요청이나 개발 데이터가 운영 실습 환경을 변경할 수 없도록 실행 권한과 저장소를 분리한다.

## 현재 구조와 완료된 리팩토링

현재 운영 앱은 호스트에서 systemd로 실행하고, 개발 앱은 별도의 관리 VM 안에서 실행한다.
개발 관리 VM은 자체 LXD로 개발 학습자 VM을 발급하므로 중첩 가상화 구조다.
nginx와 Cloudflare Tunnel이 접속을 중계하며, WebSocket 채팅은 별도 Python 서비스로 실행한다.

최근 리팩토링으로 다음 코드 경계는 이미 만들어졌다. 이 구조를 활용하고 같은 분리를 반복하지 않는다.

| 책임 | 현재 소스 |
| --- | --- |
| HTTP 진입점과 요청 처리 | `labd.py` |
| 사용자 및 관리자 화면 | `templates/` |
| 설정과 메모리 상태 | `netlab/paths.py`, `netlab/store.py` |
| 인증과 계정 생성 | `netlab/access.py` |
| VM 수명과 격리 | `netlab/instances.py`, `netlab/procs.py` |
| nginx 라우팅 적용 | `netlab/nginx.py` |
| 유지 작업과 상태 정합 | `netlab/maintainer.py` |
| 녹화 조회와 회수 | `netlab/recordings.py`, `netlab-record` |
| SQLite 연결 | `netlab/db.py` |
| 튜터와 진단 | `netlab_tutor.py`, `tutor_chat.py` |
| 채팅과 접속자 | `community_ws.py`, `community_auth.py`, `community_chat.py` |
| 배포 및 복구 | `deploy.py`, `bootstrap.py`, `netlab-backup` |

이는 소스 모듈의 분리다. 프로세스 권한, 호스트 제어 API, 개발과 운영의 자원 경계까지
분리된 것은 아니므로, 단순히 Dockerfile을 추가하는 것으로 전환을 완료하지 않는다.

## 문제 분석

아래의 영향은 현재 구조에서 해결해야 할 설계상 제약이다. 각 항목이 이미 실제 침해나
데이터 유실을 일으켰다는 주장은 아니다.

| 문제 | 소스 또는 구성 근거 | 전환 시 영향 |
| --- | --- | --- |
| 웹 서버의 호스트 관리 권한 | `labd.service`는 root로 실행하고 VM·라우팅 처리를 직접 호출 | 컨테이너에 같은 권한을 주면 앱 침해의 영향이 호스트 관리까지 이어질 수 있음 |
| 실행 환경의 차이 | 운영은 호스트, 개발은 중첩 관리 VM | Python 의존성뿐 아니라 네트워크·권한·서비스 구조가 달라 개발 검증이 운영과 달라질 수 있음 |
| 호스트 경로와 포트의 고정 | `netlab/paths.py`의 `/etc/netlab`, `/var/lib/netlab`, 고정 리스너 | 같은 호스트에 두 앱을 배치하려면 데이터·설정·외부 포트의 환경별 구성이 필요 |
| LXD 작업의 환경 식별 부재 | `procs.lxc()` 및 `instances.py`의 호출은 환경별 프로젝트를 강제하지 않음 | 앱만 두 벌 실행하면 같은 VM 목록·이미지·프로필에 접근할 수 있음 |
| 전체 호스트에 작용하는 유지 작업 | 브리지 포트 격리, VM 목록 조회, 고아 환경 회수 | 잘못된 상태나 범위로 개발 유지 작업이 운영 VM·네트워크를 건드릴 수 있음 |
| nginx 파일과 서비스의 직접 제어 | `netlab/nginx.py`의 파일 쓰기와 `systemctl reload nginx` | 웹 앱에 호스트 설정 디렉터리와 시스템 제어 권한을 노출하게 됨 |
| 프로세스 내부 상태와 잠금 | `store.py`의 전역 상태·`RLock`, 유지 스레드 | 같은 환경을 여러 앱 프로세스로 실행하면 상태 덮어쓰기·중복 유지 작업 가능 |
| 진단과 녹화의 호스트 의존 | 튜터의 `lxc exec`, 녹화의 `lxc file pull` | 웹·튜터를 컨테이너로 옮겨도 호스트 접근 경로가 필요 |
| 설치 위치에 의존한 운영 도구 | `netlab-user`의 고정 경로와 프로세스 신호, 배포의 systemd 제어 | 기존 CLI·배포·백업을 새 서비스 수명에 맞춰 연결해야 함 |
| 다중 작성자와 복구 절차 | 앱·채팅 등이 별도 DB를 작성하고 백업·복원은 호스트 서비스를 제어 | 컨테이너와 모든 작성자를 고려한 일관성 있는 백업·복원이 필요 |

앱 컨테이너에 LXD 관리 소켓, Docker 소켓, 호스트 루트 파일시스템을 전달하는 방식은
목표 권한 분리를 만족하지 않는다. LXD의 일반 로컬 관리 소켓 접근은 전체 LXD 제어를
허용하므로 호스트 root에 준하는 신뢰가 필요하다.
[LXD 보안 문서](https://canonical.com/lxd/docs/latest/explanation/security/#access-to-the-lxd-daemon)

## 목표 구조

```text
호스트 nginx와 선택적 Cloudflare Tunnel
  ├─ 운영 앱 컨테이너 + 운영 채팅 컨테이너
  │    └─ 운영 전용 설정·비밀값·DB·녹화 저장소
  └─ 개발 앱 컨테이너 + 개발 채팅 컨테이너
       └─ 개발 전용 설정·비밀값·DB·녹화 저장소

앱과 튜터
  → 환경별로 인증된 내부 관리 API
  → 호스트 관리 에이전트
       ├─ 운영 LXD 프로젝트·네트워크·학습자 VM
       └─ 개발 LXD 프로젝트·네트워크·학습자 VM
```

앱과 채팅의 이미지는 각각 개발·운영에서 동일하게 사용한다. 환경별로 달라지는 것은
설정, 비밀값, 저장소, 접속 경로, 자원 한도다. 호스트에는 LXD·스토리지·방화벽과
이를 제어하는 에이전트를 유지한다. 초기 컨테이너 운영은 Compose 기준으로 설계한다.

물리 호스트와 GPU·디스크는 계속 공유한다. 따라서 환경별 자원 제한을 적용하고,
별도 호스트 수준의 장애 격리가 필요한지는 향후 운영 규모에 따라 판단한다.

## 구현 요청 범위

### 환경 설정과 데이터 소유권

1. 환경 식별자, 앱 리스너, 데이터 루트, 설정 루트, 에이전트 주소, 외부 URL을 명시적 설정으로 만든다.
2. 개발·운영의 사용자, VM 상태, 튜터 대화, 채팅, 공지, 녹화, 비밀값을 각각 다른 저장소에 둔다.
3. 두 환경이 같은 데이터 루트나 관리 자원에 연결된 구성은 시작 전에 검출한다.
4. 비밀값은 이미지와 Git에 포함하지 않고 환경별 읽기 전용 파일 등으로 주입한다.
5. VM의 실제 상태, 소유권, 작업 상태를 누가 기록하는지 명확히 한다. 앱과 에이전트가
   각자의 파일에 상충하는 VM 소유권을 기록하는 구조를 만들지 않는다.
6. 초기에는 환경별 앱 프로세스와 유지 작업의 단일 작성자 원칙을 유지한다. 다중 replica는
   별도의 잠금·작업 조정 설계를 갖추기 전에는 지원한다고 표시하지 않는다.

SQLite는 초기 범위에서 유지할 수 있다. 컨테이너화만을 이유로 PostgreSQL이나 Redis 도입을
필수로 만들지 않는다. DB 파일은 영속 볼륨에 보관하고, 각 서비스에 필요한 파일만 노출한다.

### 호스트 관리 에이전트

호스트 전용 기능을 명시적인 인터페이스 뒤로 옮긴다. 초기 이행 단계에는 기존 함수를
감싼 구현을 둘 수 있지만, 컨테이너 앱이 호스트 명령을 직접 실행하는 경로는 최종적으로 제거한다.

| 관리 작업 | 요청 인터페이스의 예 | 에이전트에서 강제할 조건 |
| --- | --- | --- |
| VM 생성 | 승인된 템플릿과 자원 등급 | 환경별 이미지·프로필·할당량, 서버가 정한 이름과 네트워크 |
| VM 조회·시작·정지·초기화·회수 | 관리 인스턴스 ID | 환경·소유자·현재 상태·허용된 상태 전이 |
| 실습 관찰과 능동 진단 | 인스턴스 ID·노드 ID·진단 ID·허용된 매개변수 | 승인된 진단만 실행, 시간·출력·빈도 제한, 능동 진단 여부 구분 |
| 녹화 회수 | 관리 인스턴스 ID·기록 ID | 고정된 기록 루트, 경로 이탈·심볼릭 링크·용량 제한 |
| 터미널 라우팅 갱신 | 관리 인스턴스와 접속 상태 | 실제 자원에서 주소를 조회, 환경 소유 경로만 생성 |
| 상태 정합과 유지 작업 | 환경에 묶인 주기 작업 | 해당 환경만 조회·정지·회수, 중복 실행 방지 |

환경은 요청 본문의 `environment=prod` 같은 값으로 선택하게 하지 않는다.
인증된 호출 주체에 서버 측으로 묶인 환경을 사용한다. 개발 자격 증명으로 운영 인스턴스 ID,
운영 프로젝트명, 운영 경로를 넣어도 거부해야 한다.

임의 셸, 임의 `lxc` 인자, 임의 게스트 `exec`, 임의 파일 경로, 임의 프록시 IP를 받는
범용 실행 API를 만들지 않는다. 고정된 진단 구현에서 셸이 필요한 경우도 입력 검증과
대상 범위는 에이전트가 소유한다. 관리자 CLI 역시 같은 권한 규칙을 따른다.

관리 API는 인터넷이나 학습자 VM에 공개하지 않는다. 환경별 Unix 소켓 권한 또는
상호 인증된 내부 통신을 사용하고, 작업 ID·호출 환경·대상·결과를 감사 로그에 남긴다.
출력·로그·오류 응답에 프록시 비밀값, 모델 키, 인증 토큰을 넣지 않는다.

### LXD와 네트워크 분리

1. 개발·운영에 별도 LXD 프로젝트와 승인된 이미지·프로필·볼륨 사용 정책을 지정한다.
2. VM 생성뿐 아니라 조회, 스냅샷, 초기화, 파일 회수, 유지 작업, 백업까지 같은 범위를 강제한다.
3. 별도 브리지·서브넷과 호스트 방화벽 정책으로 개발·운영·학습자 간 접근을 제어한다.
   LXD 프로젝트만 나누면 네트워크까지 자동 격리된다고 가정하지 않는다.
4. 현재 브리지 격리와 게스트의 호스트 접근 차단을 새 네트워크에 맞춰 보존한다.
5. Docker 브리지와 LXD가 공유하는 FORWARD 정책을 검증한다. Docker 설치 또는 재시작으로
   기존 VM 통신이나 격리가 바뀌는 경우를 테스트한다.
6. 개발 컨테이너와 개발 VM의 CPU·메모리·디스크·프로세스 수를 제한한다.
   로그·녹화·이미지 누적으로 운영 디스크가 고갈되는 경우도 관리한다.

설치된 LXD 버전의 프로젝트·권한·네트워크 지원을 먼저 확인하고 실제 명령을 정한다.
프로젝트나 브리지 변경 과정에서 기존 운영 VM을 자동 삭제·재생성하지 않는다.

### 프록시와 외부 인증

nginx와 Tunnel은 초기에는 호스트에 유지한다. 환경별 앱·채팅·터미널 경로를 구분하고,
환경별로 발급한 내부 인증 정보와 WebSocket 접속권을 다른 환경에서 사용할 수 없게 한다.
기본 공개 접속과 선택적 Cloudflare Access·Basic 인증을 모두 유지한다.

nginx 설정 작성과 reload는 에이전트가 담당한다. 변경된 설정을 검사한 뒤 적용하고,
실패 시 이전 경로를 유지하거나 복구한다. 개발 라우팅 요청으로 운영 가상 호스트나
다른 환경의 터미널 목적지를 변경할 수 없어야 한다.

기존 URL, 터미널 연결, WebSocket 접속·재연결·로그인 갱신을 이행 전후로 검증한다.
컨테이너 이름과 내부 주소는 배포 설정으로 관리하고, 호스트 loopback 주소를 그대로
컨테이너 내부의 loopback 주소로 해석하지 않는다. AI 모델 연결도 이 조건에 포함한다.

### 이미지와 배포

- 비 root 앱·채팅 이미지와 Compose 구성을 제공한다. 불필요한 capability와 쓰기 권한은 제거한다.
- 개발·운영 Compose 프로젝트, 볼륨, 포트, 네트워크, 비밀값을 명시적으로 분리한다.
- 개발에서 검증한 이미지 digest를 운영에 승격한다. 운영용으로 소스를 다시 빌드하지 않는다.
- 이미지 버전과 설정·DB 스키마·에이전트 API의 호환 범위를 기록한다.
- 헬스 체크와 준비 상태를 구분한다. 에이전트 미접속·인증 실패 시 무한 대기나 무제한 작업 누적을 피한다.
- VM 작업은 요청 ID로 중복 실행을 방지하고 시간 초과 뒤에도 결과를 조회할 수 있게 한다.
- 유지 작업, 브리지 격리, 사용자 변경 반영이 새 프로세스 구성에서 누락되지 않게 한다.
- 현재 systemd 설치 방식은 전환 기간 동안 복귀 경로로 유지한다.

### 백업과 복구

`netlab-backup`, 계정 CLI, 녹화 CLI를 새 환경 구성에 맞게 변경한다. 코드와 이미지의 복귀,
설정 복원, DB 복원, 실습 VM 복원을 각각 구분한다. 이미지 태그를 되돌리는 것으로
비호환 DB 변경이나 LXD 자원 변경까지 복구됐다고 처리하지 않는다.

백업은 대상 환경의 모든 작성자를 고려해야 한다. 앱·채팅·튜터·유지 작업을 일관되게
중지하거나 SQLite 백업 API 등 검증된 스냅샷 절차를 사용한다. 개발 백업이 운영 DB를
잠그거나 운영 VM을 정지할 수 없어야 한다. 복원은 빈 대상 또는 충돌 검사를 통과한
명시적 대상에서 진행하고, 사용자에게 실제로 복원 가능한 결과인지 검증한다.

## 단계별 진행 순서와 승인 조건

| 단계 | 구현 범위 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1 | 현재 HTTP·인증·채팅·VM 동작의 기준선, 자원 목록, 백업·복원 절차 확보 | 현재 데이터와 VM의 소유권을 식별하고 회귀 테스트 기준선 확보 |
| 2 | 환경 설정, 경로·포트 주입, 호스트 제어 인터페이스와 단일 상태 소유권 정리 | 기존 실행 방식의 동작 유지, 환경 충돌 검출 테스트 통과 |
| 3 | 에이전트 구현, 개발·운영 권한과 LXD 프로젝트·네트워크 범위 강제 | 위조한 환경·VM·경로·작업을 거부하는 테스트 통과 |
| 4 | 앱·채팅 이미지와 Compose 작성, 개발 환경을 호스트 컨테이너로 실행 | 실제 개발 브라우저·실습·채팅·튜터·장애 복구 검증 통과 |
| 5 | 동일 이미지로 운영 병행 점검 후 접속 경로 전환 | 데이터·VM 매핑 확인, 중복 유지 작업 방지, 복귀 절차 사전 검증 |
| 6 | 안정화 후 구 개발 관리 VM과 구 앱 실행 구성 정리 | 보존 기간 경과, 필요한 데이터·기록·스냅샷 확인, 별도 정리 승인 |

구 개발 관리 VM 제거와 기존 운영 VM의 프로젝트 이동·네트워크 재구성은 코드 리팩토링과
분리한 작업으로 취급한다. 대상을 확정하고 백업·중단 영향·복귀 방법을 제시한 뒤 실행한다.

## 검증과 완료 기준

### 기능 회귀

- 공개 guest와 인증 계정의 로그인·역할·관리자 권한이 유지된다.
- VM 발급·재사용·시작·정지·초기화·회수·웜 풀·유휴 정책·재시작 상태 정합이 동작한다.
- 터미널, 녹화 회수와 재생, 교재 링크, 튜터의 단원 감지·모델 선택·진단이 유지된다.
- 채팅 메시지·접속자·여러 탭 집계·전송 중복 방지·재연결·접속권 갱신이 동작한다.

### 환경 격리

- 개발 자격 증명과 변조된 요청으로 운영 VM·스냅샷·파일·DB·프록시를 읽거나 변경할 수 없다.
- 프로젝트를 생략하거나 다른 프로젝트명을 보내도 에이전트가 승인된 범위를 강제한다.
- 고아 회수·유휴 정지·브리지 격리·백업·복원이 다른 환경에 영향을 주지 않는다.
- 개발·운영 앱과 학습자 VM에서 에이전트·호스트·다른 환경으로 허용되지 않은 통신이 차단된다.
- 앱 컨테이너에서 LXD·Docker 소켓, 호스트 root, 다른 환경의 비밀값에 접근할 수 없다.

### 배포와 장애

- 개발·운영의 이미지 digest가 일치하고 환경별 설정·저장소는 분리돼 있다.
- 앱·채팅 재시작 시 DB·녹화·실습 VM은 보존되고 접속자가 재연결된다.
- 에이전트 또는 LXD 응답 지연, 생성 중 재시작, 중복 요청에도 중복 VM·소유권 누락이 생기지 않는다.
- 개발 부하 한도를 초과하는 시험에서 운영의 허용 가능한 지연·오류 기준을 유지한다.
  그 기준과 시험 부하는 운영 전환 전에 수치로 정한다.
- 빈 복원 환경에서 백업 복원과 코드·이미지 롤백을 실제로 확인한다.
- 기존 HTTP 동등성 검사와 단위 테스트에 더해 실제 호스트·컨테이너·LXD 통합 검증을 수행한다.

## 산출물

1. 환경 경계, 상태 소유권, 호스트 에이전트 인증과 API 계약 문서.
2. 설정 예제, 앱·채팅 Dockerfile, Compose, 에이전트 서비스와 설치 스크립트.
3. 환경별 LXD 프로젝트·네트워크·프로필·한도 구성과 자원 매핑 점검 도구.
4. 환경 격리·인증·VM 수명·진단·WebSocket·복구를 검증하는 자동 테스트와 실측 결과.
5. 기존 데이터·VM을 보존하는 개발 이행, 운영 전환, 롤백 실행서.
6. 설치·업데이트·백업·장애 진단·비밀값 교체에 대한 운영 가이드.

현재 문서와 실행 방식의 전제는 [서버 안내](README.md), 모듈 역할은
[`netlab/__init__.py`](netlab/__init__.py), 호스트 권한은
[`labd.service`](systemd/labd.service)를 기준으로 확인한다.

## 이번 요청에서 제외하는 작업

Kubernetes 도입, PostgreSQL·Redis 전환, 실습 VM의 컨테이너 대체, GPU 모델 서빙의 재설계,
전체 호스트 HA 구성은 이번 범위에 넣지 않는다. 새 구조에 반드시 필요한 호환 작업이
발견되면 근거와 변경 범위를 제시한다. 구현 착수 전에는 이 요청서만으로 운영 자원을
삭제하거나 환경을 전환하지 않는다.
